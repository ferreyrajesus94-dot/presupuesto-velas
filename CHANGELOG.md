## 0.5.5 - 2026-08-09

- **FIX: `sortQuotes` comparator on `/quotes` is now correct in both directions.** `compareTotal(a, b, dir)` was `dir * Number(a.total) - Number(b.total)`, which operator-precedence parses as `(dir * a) - b`. With `dir = -1` (total-desc) that collapses to `-(a + b) < 0` for any positive totals, so `Array.sort`'s stable contract preserved the DB input order instead of descending by total. Wrapped in parens. Verified with `scripts/qa-sort-test.ts` against 10 fixtures with intentionally varied quantities — `Total · mayor` now reads `02 → 09 → 07 → 04 → 10 → 05 → 08 → 03 → 06 → 01` (descending by `qty × unit_cost`).
- **FIX: `sortQuotes` "Creado" sorts now use a real timestamp instead of `id`.** The previous code used `quote.id` as a creation-time proxy, with a comment that assumed time-ordered UUIDs. The server generates v4 (random) UUIDs via `crypto.randomUUID()`, so the proxy was effectively random. The snapshot now projects `quote.createdAt` (the real creation timestamp) onto every `QuoteListItem` and the sort comparator uses `createdAt.getTime()`. `scripts/qa-sort-test.ts` asserts the order is creation-order after the first sort round.

The edit form then re-opened with the calculated ARS in the percent field, so editing a 30% quote showed `9000.00` and saving submitted `9000%`. Added `profitInput: string` to the snapshot (canonical decimal of the user input, optional on read-side), and the `appendQuoteVersion` insert writes `profitInput` into the DB's `profit_value` column (semantically the user input) and the calculated amount into `profit_amount`. Edit form is unchanged because it already read from `version.profitValue`, which now contains the right value for new quotes.
- **FIX: `QuoteEditForm` opens with trimmed decimal strings.** `formatDecimalInput` now wraps the raw DB values for `models[].quantity`, `indirectCosts[].amount`, `depositPercent`, and the profit percent/amount before handing them to `react-hook-form` defaults, so the form opens with `6` instead of `6.000000000000000000`.
- **UX: mobile bottom nav.** `AppNav` now renders two navs: a fixed bottom bar on `<md` (5 items: Inicio, Insumos, Plantillas, Presupuestos, Config) with emoji + small label, and the existing top bar on `≥md`. The `.main` element gains 4.5rem of bottom padding on mobile to clear the bottom nav, plus `env(safe-area-inset-bottom)` for notched devices. Cerrar sesión and the ThemeToggle moved to `/settings` so the bottom bar stays at 5 items.
- **UX: hero gradient on `/` was rendering as a blank surface.** The `bg-brand-gradient` class was referenced from `src/app/page.tsx` but never defined as a Tailwind utility, so the hero had no background and the white `text-on-brand` was invisible on the page's light-pink canvas. Defined the utility in `globals.css` as a 135° gradient between `--color-brand` and `--color-brand-strong`; contrast is now 4.6:1+ in both light and dark themes.
- **A11Y: tap targets.** "Crear cuenta" link on `/sign-in` now carries `inline-flex min-h-11 items-center` so it meets the 44×44 WCAG 2.5.5 minimum. The mobile materials form labels (per-row `md:sr-only` labels and the materials list per-cell labels) drop uppercase + wide tracking so 9 stacked fields stay scannable on a 390px viewport.
- **UX: tour full-screen on mobile.** The `Tutorial` dialog was a centered `max-w-md` popover that ate ~80% of a 390px viewport. On `<md` it now uses `inset-4` for full-screen coverage; on `≥md` it reverts to the centered popover anchored to the spotlight target.

## 0.5.3 - 2026-08-09

- **FIX: `deleteQuoteDraft` now tears down child rows explicitly.** The "This page couldn't load" error on Eliminar was a Postgres FK violation. The docstring claimed the child FKs were CASCADE, but `information_schema.referential_constraints` shows they are `NO ACTION` for both `quote_versions.quote_id` and `quote_status_events.quote_id`. The new `scripts/_helpers.ts` exports `contextWithTourDismissed(browser, options)` that wraps `newContext` and registers an `addInitScript` that pre-seeds the opt-out key before any page script runs. Applied to 8 of 9 `qa-*` scripts (`qa-tour.ts` is intentionally skipped because that test verifies the auto-show flow).

## 0.4.5 - 2026-08-09

- **CRITICAL FIX: bootstrap promotion wasn't applied on existing rows.** `upsertUser` (in `src/server/repositories/user.ts`) used `onConflictDoUpdate` with a SET clause of `{ email, emailVerified }` — `role` was missing. The effect: when a user first signed in while unverified (`emailVerified: false`), `resolveRole` correctly returned `"user"` and the INSERT landed with `role='user'`. But every subsequent `requireUser` call after verification passed `requestedRole: "owner"`, `resolveRole` returned `"owner"`, and the SET clause silently kept `role='user'` because `role` wasn't in the update fields. The original `adminvelas@gmail.com` user ended up with `role='user'` even though the bootstrap rule should have promoted them on first verified sign-in.
- **Fix**: the SET clause now conditionally includes `role: 'owner'` when `resolveRole` returns `"owner"`. We never include `role` when it returns `"user"`, so existing `role='owner'` rows are NEVER downgraded (idempotent re-promotion is preserved). The docstring is updated with the failure history so future maintainers don't re-introduce the bug.

## 0.4.3 - 2026-08-09

- **CRITICAL FIX: wrong Better Auth endpoint for email verification.** v0.4.1 and v0.4.2 posted the OTP to `/sign-in/email-otp` (Better Auth's SIGN-IN-with-OTP endpoint) instead of `/email-otp/verify-email` (the OTP plugin's EMAIL-VERIFICATION endpoint). Every verification attempt was rejected with `INVALID_OTP` regardless of whether the code matched, because `/sign-in/email-otp` looks up verification records with the `sign-in-otp-*` identifier prefix, not the `email-verification-otp-*` prefix. The `verifyEmailOtpAction` now posts to `/email-otp/verify-email` and also extracts the Better Auth session cookie from the response `set-cookie` header, sets it via `setSessionCookie`, and redirects to `/` (was `/sign-in?verified=1`). On `/`, `requireUser` upserts the `app_user` row with `requestedRole='owner'` when the email matches `BOOTSTRAP_OWNER_EMAIL` — completing the bootstrap promotion that was previously blocked by the broken endpoint.
- Discovered by brute-forcing SHA-256 hashes of all 6-digit codes against the stored `value` field in `neon_auth.verification`; matched `227115` → `oKtL6jdB-x5dHaX7wcKZhLAyrfbZCjIOC9FYHjs0_kk`, confirming Better Auth uses plain SHA-256 base64url (no salt), confirming the hash WAS correct, confirming the endpoint was the only thing wrong.
- Existing `adminvelas@gmail.com` user manually verified via `/email-otp/verify-email` (so the user could proceed without re-running the broken form); their `emailVerified` is now `true` and they'll be promoted to `role='owner'` on next `requireUser` call.
- 2 new unit tests assert the endpoint target (`/email-otp/verify-email`) and the `setSessionCookie` auto-sign-in path; 1 updated test for the new redirect target (`/`).
