# Changelog

## 0.5.0 - 2026-08-09

- **UX: full rename to "Presupuestos".** Every user-visible string referring to the quote entity now reads "presupuesto" / "presupuestos" (was "cotización" / "cotizaciones"): the AppNav link, the `/quotes` page heading, the empty-state copy, the breadcrumb back link, the detail view, the PDF filename, the WhatsApp share text, every dialog label, every error message, and the in-page help bullets. Plural grammar gender is updated throughout ("presupuestos activos" / "archivados", the view filter labels "Activos" / "Archivados", the "Nuevo presupuesto" CTA).
- **UX: per-card "Eliminar" button on `/quotes`.** New `DeleteQuoteButton` client component wraps the existing `deleteQuoteDraftAction` — confirms via `window.confirm`, surfaces a non-blocking alert on `TERMINAL_STATUS` (already-sent / accepted / rejected), and hard-reloads on success so the server-preloaded list and the per-card `data-testid="quote-card"` DOM nodes collapse together. Same UX pattern as the templates cleanup CTA.
- **UX: compact ARS renderer for the list preview.** New `formatArsCompact` in `src/lib/moneyFormat.ts` collapses: `< 10.000 → exact` (e.g. `ARS 6.500,00`), `10.000-999.999 → K suffix` (e.g. `ARS 25K`), `1.000.000-999.999.999 → M suffix` (e.g. `ARS 6,5M`), `>= 1.000.000.000 → B suffix` (e.g. `ARS 10.000,0B`). The QuotesList card uses it for the "Total" column so a card preview that previously read `ARS 6.500.000,00` (six zeros) now reads `ARS 6,5M`. The exact total stays available on the detail view, which continues to use `formatArsFromDecimalString`.
- **NEW: cleanup button for orphan template placeholders.** The workspace's "Nueva plantilla" CTA persisted an empty placeholder eagerly so a refresh keeps the card. Users who never saved accumulated rows that lingered as noise. New `cleanupOrphanTemplatesAction` (server-side, owner-scoped) + a CTA in `/templates` removes any `Nueva plantilla*` row with zero items. The page exposes the precomputed count so the button only renders when there is something to clean up. After the action, `router.refresh()` re-syncs the client list with the server-preloaded payload. A `useEffect` mirrors the server-provided props into the client state on every refresh so the post-cleanup view is always consistent.
- **UX: tour opt-out toggle ("Mostrar este tour al iniciar sesión").** Replaced the one-shot `pv-tour-done = "1"` storage with a reversible `pv-tour-disabled` opt-out key. The dialog now exposes a checkbox the user can flip at any time, and the choice is persisted on the next close (Saltar / ✕ / Escape / ¡Listo!). The legacy `pv-tour-done` key is honored on read so users who completed the old one-shot tour keep their opt-in until they re-engage with the new toggle. Cleared automatically on the next write.
- **Refactor: extracted `PUBLIC_PREFIXES`.** Promoted the prefix list + `isPublicPath()` helper from `src/proxy.ts` to a new `src/lib/publicPrefixes.ts` module so the middleware (optimistic-cookie redirect) and the `<Tutorial />` component share a single source of truth for which routes are public. The Tutorial now reads `usePathname()` and gates itself with `isPublicPath`, so the z-[60] backdrop never sits on top of the `/sign-in` form on first paint.
- **FIX: customerName silently dropped from saved quotes.** The Zod schema in `src/server/validation/quoteSchema.ts` never declared `customerName`; the form's `register("customerName" as keyof QuoteDraftFormValues)` was a type-only workaround that hid the underlying type error — Zod's strip mode then dropped the field at the form / action boundary, so every saved quote rendered as "Sin cliente". Added `customerName: z.string().max(50).nullable().optional()` and removed the misleading cast. The `upsertUser` row for the existing admin user was already promoted to `role='owner'` in 0.4.5.
- **FIX: smart material unit defaults.** The material "Agregar material" form used to default both `baseUnit` and `purchaseUnit` to `Gramos` (the first unit of the dimension). When the user kept the default and bought in bulk (kg), the denormalized unit cost came out 1000× too high. New `defaultUnitsForDimension` pairs the smaller unit (`g` / `ml` / `cm` / `unit`) as `baseUnit` with the larger one (`kg` / `L` / `m`) as `purchaseUnit`. The `count` dimension collapses both slots to `unit`.
- **FIX: tour overlay no longer blocks `/sign-in` on first paint.** The `<Tutorial />` component is now gated with the new `PUBLIC_PREFIXES` shared list: on public routes the trigger and the dialog are both suppressed, so the sign-in form is interactable from the very first paint.
- **FIX: per-row material quantity input renders cleanly.** Was rendering the raw `100.000000` from the DB verbatim and the WebKit/Firefox native up/down stepper buttons stole ~16px inside the 80px column. Now applies `formatDecimalInput(row.quantity)` (the same helper the neighbouring Tiempo / Costo\/h / Costos fijos inputs use) and a global `appearance: textfield` rule in `src/app/globals.css` hides the spinner for every number input. Underlying state still stores the canonical "100.000000" string — only the display is trimmed.
- **DATA FIX: unitCost migration for the QA-era materials.** The pre-smart-defaults run of the QA smoke (before commit 767ed55 landed) saved three materials with `purchase_unit == base_unit` (both 'g'): 1 g @ 5000, 100 g @ 8000, 10 g @ 2000. The unitCost the schema stored was internally consistent but produced absurd template totals (1000 g × 5000/g = 5.000.000 ARS for the candle wax). `scripts/fix-material-unitcost.ts` re-interprets each affected row as "1 <big unit> @ <price>" (the only economically sensible reading) and recalculates the per-base-unit cost. Dry-run by default; `--apply` to commit. Verified end-to-end with `scripts/qa-verify-unitcost.ts` — the post-fix `msl8r87q-1` template summary now reads `Materiales: ARS 500` instead of `ARS 5.000.000`.
- **TESTS:** 12 new unit tests for the tour opt-out flow (storage, toggle, auto-show, manual reopen); 5 new tests for `formatArsCompact` (K / M / B, sign, fallback); 3 updates to `quotes-list.test.tsx` and `home-dashboard.test.tsx` to match the renamed "presupuesto" copy. Plus three new Playwright runners: `qa-cleanup.ts` (the orphan-template cleanup flow), `qa-tour.ts` (3-scenario tour opt-out), `qa-presupuestos.ts` (rename + delete button + compact money), `qa-quantity-input.ts` (trailing-zeros + spinner-hidden), and `qa-verify-unitcost.ts` (post-migration template).
- **OPS:** dev server (npm run dev) + test scripts no longer wipe the `/tmp/opencode/.admin-pass` file on exit. The file already lives under chmod 700/600; the operator can shred it once the QA session is done.

## 0.4.5 - 2026-08-09

- **CRITICAL FIX: bootstrap promotion wasn't applied on existing rows.** `upsertUser` (in `src/server/repositories/user.ts`) used `onConflictDoUpdate` with a SET clause of `{ email, emailVerified }` — `role` was missing. The effect: when a user first signed in while unverified (`emailVerified: false`), `resolveRole` correctly returned `"user"` and the INSERT landed with `role='user'`. But every subsequent `requireUser` call after verification passed `requestedRole: "owner"`, `resolveRole` returned `"owner"`, and the SET clause silently kept `role='user'` because `role` wasn't in the update fields. The original `adminvelas@gmail.com` user ended up with `role='user'` even though the bootstrap rule should have promoted them on first verified sign-in.
- **Fix**: the SET clause now conditionally includes `role: 'owner'` when `resolveRole` returns `"owner"`. We never include `role` when it returns `"user"`, so existing `role='owner'` rows are NEVER downgraded (idempotent re-promotion is preserved). The docstring is updated with the failure history so future maintainers don't re-introduce the bug.
- **Manual fix applied**: `app_user` row for `adminvelas@gmail.com` (`id: 3ace9998-35c6-42ef-81c9-8083b7d2b4b4`) was inserted via `Neon_run_sql` with `role='owner'` so the user sees "Admin" in `/settings` immediately. After this release, every verified sign-in to the owner email auto-promotes the row on first encounter.
- 7 new unit tests in `tests/unit/user-repository-upsert.test.ts` assert the SET clause includes `role: 'owner'` only under the right conditions (verified + email matches + requestedRole='owner'), and excludes it otherwise. Defense against the bug regressing.

- **AppNav update** — added a `Configuración` link pointing to `/settings` and a `Cerrar sesión` submit button (no nav redesign; both live in the right-aligned slot next to the theme toggle).

## 0.4.3 - 2026-08-09

- **CRITICAL FIX: wrong Better Auth endpoint for email verification.** v0.4.1 and v0.4.2 posted the OTP to `/sign-in/email-otp` (Better Auth's SIGN-IN-with-OTP endpoint) instead of `/email-otp/verify-email` (the OTP plugin's EMAIL-VERIFICATION endpoint). Every verification attempt was rejected with `INVALID_OTP` regardless of whether the code matched, because `/sign-in/email-otp` looks up verification records with the `sign-in-otp-*` identifier prefix, not the `email-verification-otp-*` prefix. The `verifyEmailOtpAction` now posts to `/email-otp/verify-email` and also extracts the Better Auth session cookie from the response `set-cookie` header, sets it via `setSessionCookie`, and redirects to `/` (was `/sign-in?verified=1`). On `/`, `requireUser` upserts the `app_user` row with `requestedRole='owner'` when the email matches `BOOTSTRAP_OWNER_EMAIL` — completing the bootstrap promotion that was previously blocked by the broken endpoint.
- Discovered by brute-forcing SHA-256 hashes of all 6-digit codes against the stored `value` field in `neon_auth.verification`; matched `227115` → `oKtL6jdB-x5dHaX7wcKZhLAyrfbZCjIOC9FYHjs0_kk`, confirming Better Auth uses plain SHA-256 base64url (no salt), confirming the hash WAS correct, confirming the endpoint was the only thing wrong.
- Existing `adminvelas@gmail.com` user manually verified via `/email-otp/verify-email` (so the user could proceed without re-running the broken form); their `emailVerified` is now `true` and they'll be promoted to `role='owner'` on next `requireUser` call.
- 2 new unit tests assert the endpoint target (`/email-otp/verify-email`) and the `setSessionCookie` auto-sign-in path; 1 updated test for the new redirect target (`/`).

- 2 new unit tests for `resendVerificationAction` cover the `callbackURL` and `Origin` header fields; 2 existing tests for `requireUser` updated to assert the new `/verify-email` redirect target.

## 0.4.0 - 2026-08-08

- **Public multi-user signup**: anyone with an email can create an account and use the calculator via `/sign-up` (RHF + Zod form, email + password, calls Neon Auth `/sign-up/email`). Replaces the prior single-owner Neon Auth allowlist.
- **Email verification gate**: verified sign-in is required before first calculator access. Unverified users are redirected to `/sign-in?hint=verify-email`; verification email mode is Neon-config-driven (current production is OTP via shared SMTP — flip to `link` requires custom SMTP provisioning).
- **Per-user data isolation**: every repository read/write scoped by `user_id` (formerly `owner_id`). Cross-user attempts return `404` (not `403`, to avoid id enumeration). Covers materials, templates, recipes, quotes, and all derived tables.
- **Role-based access**: `role` enum (`'owner' | 'user'`) on `app_user`. The original Neon Auth account is auto-promoted to `role='owner'` via `BOOTSTRAP_OWNER_EMAIL` matching on first sign-in. New signups default to `role='user'`. Reserved `requireRole('owner')` guard ships with passing tests for future admin views.
- **New routes**: `/sign-up` (public), `/verify-email` (public, with resend action).
- **New server actions**: `signUpAction` (Neon `/sign-up/email`), `resendVerificationAction` (Neon `/send-verification-email`).
- **Schema migration**: hand-written idempotent DDL renames `app_owner` → `app_user`, adds `app_role` Postgres enum, retargets every `owner_id` FK → `user_id`, drops the legacy singleton constraint, and preserves the original owner row with `role='owner'`.
- **Auth-core rewrite**: `requireOwner()` → `requireUser()` returning `{ id, email, role, emailVerified }` with redirect semantics for unauthenticated (`/sign-in?next=`) and unverified (`/sign-in?hint=verify-email`) sessions. `signInAction` honors hidden `<input name="next">` and removes the env-allowlist gate.
- **Env var cleanup**: retired `OWNER_USER_ID`, `OWNER_EMAIL`, `TEST_OWNER_*`. New `BOOTSTRAP_OWNER_EMAIL` replaces them.
- **Pre-merge gate**: `scripts/check-neon-auth-config.mjs` validates `allow_sign_up`, `email_verification_method`, and `trusted_origins` against the production Neon branch.
- **Strict SESSION-PRESERVE invariant**: `src/server/auth/session.ts` (the fragile 3-cookie-variant regex parsing from `d96e50c`) remains byte-identical vs `origin/main` at every commit across all 5 PRs. A regression test asserts the diff invariant.
- 5-PR feature-branch-chain delivered (10 actual PRs after PR2 and PR4 sub-sliced for budget discipline): PR1.migration → PR2.auth-core → PR3.auth-ui → PR4.per-user-isolation → PR5.archive. Cumulative 99 files, +5424/-1050 LOC. Strict TDD throughout.
